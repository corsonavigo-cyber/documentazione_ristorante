======================================================================
1. DESCRIZIONE DEL PROGETTO
======================================================================

Il progetto è un gestionale web per la gestione operativa di un
ristorante.

Il sistema permette di gestire:

- tavoli
- prenotazioni
- menu
- piatti
- bevande
- allergeni
- momenti del servizio
- ordini
- comande
- stato degli ordini
- conti
- scontrini
- IVA
- stampa di comande e scontrini

L'applicazione è organizzata separando:

- frontend
- API
- logica applicativa
- accesso al database
- gestione della stampa

======================================================================
3. STRUTTURA LOGICA DELL'APPLICAZIONE
======================================================================

Il flusso generale dell'applicazione è:

    FRONTEND
       |
       | HTTP / Fetch
       v
    API PHP
       |
       v
    SERVICE
       |
       v
    REPOSITORY
       |
       v
    DATABASE


Il frontend non accede direttamente al database.

Le richieste vengono inviate alle API PHP.

Le API delegano la logica applicativa ai Service.

I Service utilizzano i Repository per eseguire le operazioni
sul database.


======================================================================
4. BACKEND
======================================================================

Il backend è organizzato principalmente in:

- API
- Service
- Repository
- configurazione
- gestione database
- gestione stampa


----------------------------------------------------------------------
4.1 DATABASE
----------------------------------------------------------------------

La connessione al database viene gestita tramite PDO.

La configurazione viene mantenuta tramite variabili d'ambiente
contenute nel file:

    .env

Le credenziali del database non devono essere inserite direttamente
nel codice sorgente.

La connessione viene centralizzata attraverso la classe Database.


----------------------------------------------------------------------
4.2 REPOSITORY
----------------------------------------------------------------------

I Repository hanno il compito di gestire l'accesso ai dati.

Le responsabilità principali sono:

- SELECT
- INSERT
- UPDATE
- DELETE
- gestione delle relazioni
- transazioni

Il Repository non dovrebbe contenere la logica relativa
all'interfaccia utente.


----------------------------------------------------------------------
4.3 SERVICE
----------------------------------------------------------------------

I Service contengono la logica applicativa.

Sono responsabili di coordinare più operazioni del Repository
quando una funzionalità richiede più passaggi.

Esempio:

    aggiornamento di una comanda

        |
        +--> aggiornamento ordine
        |
        +--> eliminazione vecchie relazioni
        |
        +--> inserimento nuove relazioni
        |
        +--> commit


======================================================================
5. API
======================================================================

Le API espongono le funzionalità del gestionale tramite richieste HTTP.

Esempi di endpoint:

    /api/tavoli.php

    /api/menu.php

    /api/prenotazioni.php

    /api/ordini.php

    /api/scontrino.php


Le funzionalità specifiche vengono selezionate tramite parametri
come:

    ?type=...


Esempio:

    /api/menu.php?type=menu

    /api/ordini.php?type=oggi

    /api/scontrino.php?type=iva


======================================================================
6. GESTIONE DEI TAVOLI
======================================================================

Il sistema permette di:

- visualizzare i tavoli
- inserire tavoli
- modificare tavoli
- eliminare tavoli
- controllare la disponibilità
- associare tavoli agli ordini
- associare tavoli alle prenotazioni


Un ordine può essere associato a uno o più tavoli.


======================================================================
7. PRENOTAZIONI
======================================================================

Le prenotazioni permettono di associare:

    prenotazione
        |
        +--> data
        +--> orario
        +--> numero persone
        +--> tavoli


Le relazioni tra prenotazioni e tavoli vengono gestite
separatamente.


======================================================================
8. MENU
======================================================================

Il menu gestisce gli elementi disponibili per il servizio.

Gli elementi possono essere:

- piatti
- bevande

Ogni elemento può avere:

- nome
- descrizione
- prezzo
- IVA
- categoria
- disponibilità
- allergeni


Gli allergeni vengono gestiti tramite una relazione dedicata.


======================================================================
9. MOMENTI DEL SERVIZIO
======================================================================

Gli ordini sono organizzati in base al momento del servizio.

Configurazione attuale:

    1 = Antipasto
    2 = Primo
    3 = Secondo
    4 = Dolci
    5 = Da evadere subito


Il momento viene associato alla singola voce della comanda.

Questo permette di modificare l'ordine di evasione senza modificare
necessariamente l'elemento del menu.


======================================================================
10. ORDINI
======================================================================

L'ordine rappresenta la sessione di servizio associata al tavolo.

Un ordine può contenere:

- numero persone
- tavoli
- elementi ordinati
- momenti del servizio
- stato
- conto
- scontrino


Le relazioni principali sono:

    ORDINE
       |
       +--> TAVOLI
       |
       +--> ITEM
       |
       +--> STATO
       |
       +--> MOMENTO DEL SERVIZIO
       |
       +--> CONTO
       |
       +--> SCONTRINO


======================================================================
11. COMANDA
======================================================================

La comanda rappresenta gli elementi ordinati.

Una voce della comanda è identificata logicamente almeno da:

    id_item
    id_momento

Questo permette di avere lo stesso elemento in momenti differenti.


Una voce può inoltre contenere:

    quantità
    nota


Esempio concettuale:

    Pizza Margherita
    quantità: 2
    momento: Secondo
    nota: senza mozzarella


======================================================================
12. GESTIONE DELLO STATO FRONTEND
======================================================================

Il frontend mantiene lo stato corrente dell'ordine.

La struttura utilizzata comprende informazioni come:

    state = {
        comanda: [],
        items: [],
        momenti: [],
        tavoliInUso: [],
        momentoAttivo: 1,
        idOrdineInserito: null,
        confirmGiaChiesto: false
    }


La chiave utilizzata per LocalStorage è:

    id_ordine


Il LocalStorage viene utilizzato per mantenere lo stato
temporaneo della lavorazione dell'ordine.


======================================================================
13. AGGIORNAMENTO DELLA COMANDA
======================================================================

L'aggiornamento della comanda viene effettuato inviando
la nuova comanda al backend.

Il frontend non deve essere considerato come livello di sicurezza.

Il backend riceve la nuova comanda e sostituisce le relazioni
precedenti.


Flusso:

    FRONTEND
       |
       | PUT /api/ordini.php?type=comanda
       |
       v
    SERVICE
       |
       v
    TRANSAZIONE
       |
       +--> aggiorna ordine
       |
       +--> elimina vecchie relazioni
       |
       +--> inserisce nuove relazioni
       |
       +--> COMMIT


In caso di errore:

       |
       v
    ROLLBACK


Questo garantisce che l'aggiornamento non rimanga in uno stato
parzialmente applicato.


======================================================================
14. TRANSAZIONI
======================================================================

Le operazioni che modificano più tabelle devono essere eseguite
all'interno di una transazione.

Schema:

    BEGIN
       |
       +--> operazione 1
       |
       +--> operazione 2
       |
       +--> operazione 3
       |
       v
    COMMIT


In caso di eccezione:

    BEGIN
       |
       +--> operazione 1
       |
       +--> operazione 2
       |
       X--> errore
       |
       v
    ROLLBACK


Questo approccio evita dati incoerenti.


======================================================================
15. STATO DEGLI ORDINI
======================================================================

Gli ordini possono attraversare differenti stati.

Lo stato viene gestito tramite una relazione dedicata.

Il frontend utilizza lo stato per determinare:

- visualizzazione
- possibilità di modifica
- evasione
- chiusura
- gestione del conto


======================================================================
16. STAMPA DELLE COMANDE
======================================================================

La stampa delle comande viene gestita dal componente StampaService.

La comanda viene separata in:

    CUCINA
    BAR


Gli elementi vengono quindi inviati al rispettivo output di stampa.


Il metodo principale utilizzato per la generazione è:

    generaComandaTxt()


Il metodo supporta anche la gestione delle modifiche alla comanda.


======================================================================
17. SCONTRINI
======================================================================

Gli scontrini vengono gestiti tramite:

    scontrino_emesso

e le relative informazioni di dettaglio.


Lo scontrino contiene informazioni come:

    id_scontrino
    id_ordine
    data_e_ora_pagamento
    totale


Il dettaglio contiene invece le singole voci dello scontrino.


Questa separazione permette di mantenere:

    SCONTRINO
        |
        +--> voce 1
        +--> voce 2
        +--> voce 3
        +--> ...


======================================================================
18. STORICIZZAZIONE DEI PREZZI
======================================================================

Per gli scontrini viene utilizzato il prezzo storico dell'elemento.

Questo è importante perché il prezzo presente nel menu può cambiare
dopo l'emissione dello scontrino.

Lo scontrino deve invece mantenere il valore utilizzato
al momento della vendita.

Vengono quindi utilizzati valori come:

    prezzo_unitario_storico
    aliquota_iva_storica


======================================================================
19. CALCOLO IVA
======================================================================

L'IVA dello scontrino viene calcolata utilizzando:

    prezzo_unitario_storico
    aliquota_iva_storica
    quantità


L'IVA viene calcolata per ogni voce e successivamente aggregata.

Il sistema espone inoltre un endpoint dedicato al recupero
delle aliquote IVA storiche:

    /api/scontrino.php?type=iva


======================================================================
20. STAMPA DELLO SCONTRINO
======================================================================

La generazione dello scontrino viene gestita tramite:

    generaScontrinoTxt()


I dati vengono recuperati dal database e passati
al formatter dello scontrino.

Il metodo principale di formattazione è:

    formattaScontrino()


La formattazione può gestire:

    scontrino normale
    ristampa
    storno
    annullamento


======================================================================
21. STORNI E ANNULLAMENTI
======================================================================

Gli storni vengono distinti dalla normale emissione.

Il valore:

    active = 0

viene utilizzato nel caso dello storno/cancellazione.

L'annullamento deve comunque generare una stampa che riporti
esplicitamente lo stato di annullamento.


La stampa non deve quindi essere omessa semplicemente perché
l'elemento non è più attivo.

23. API GENERICHE JAVASCRIPT
======================================================================

Le chiamate HTTP vengono centralizzate attraverso funzioni
riutilizzabili.

L'obiettivo è evitare di duplicare continuamente:

    fetch()
    gestione URL
    headers
    parsing JSON
    gestione errori


I parametri delle richieste vengono gestiti tramite
URLSearchParams quando appropriato.


======================================================================
24. RENDERING DELLA COMANDA
======================================================================

Il rendering della comanda viene effettuato a partire dallo stato
frontend.

Funzioni principali:

    aggiornaVoceComanda()
    trovaVoce()
    eliminaVoce()
    renderVoce()
    disegnaPreComanda()
    totaleComanda()


Il rendering raggruppa gli elementi per momento del servizio.


======================================================================
25. GESTIONE QUANTITA' E NOTE
======================================================================

La quantità e la nota vengono gestite direttamente
sulle voci della comanda.

La logica frontend permette di:

- modificare quantità
- inserire note
- aggiornare la voce
- ricalcolare il totale
- salvare lo stato


La nota non deve generare necessariamente una nuova voce
se la logica applicativa richiede l'aggregazione dell'elemento.


======================================================================
26. GESTIONE DEL CONTO
======================================================================

Il conto rappresenta la fase finale dell'ordine.

Le informazioni utilizzate per il conto comprendono:

- elementi ordinati
- quantità
- prezzi
- sconti
- IVA
- totale


Il frontend può gestire lo sconto applicato al totale della
precomanda, mentre i dati definitivi devono essere consolidati
dal backend.

======================================================================
28. SICUREZZA
======================================================================

Le query al database devono utilizzare prepared statements PDO.

Non devono essere concatenate direttamente variabili provenienti
dalle richieste HTTP nelle query SQL.

Le credenziali devono essere mantenute nel file:

    .env

Il file .env non deve essere pubblicato nel repository Git.


Il backend deve validare sempre:

- ID
- tipi di dato
- quantità
- array ricevuti
- valori obbligatori
- autorizzazioni


La validazione frontend è utile per l'esperienza utente,
ma non sostituisce la validazione backend.


======================================================================
29. GESTIONE DEGLI ERRORI
======================================================================

Gli errori devono essere gestiti a più livelli.

FRONTEND
--------

Gestire:

- errori HTTP
- risposte non valide
- errori di rete
- errori di parsing JSON


BACKEND
-------

Gestire:

- eccezioni PDO
- dati non validi
- risorse inesistenti
- errori durante transazioni


DATABASE
--------

Le operazioni critiche devono essere protette
da transazioni.

30. PATTERN ARCHITETTURALI
======================================================================

REPOSITORY PATTERN
------------------

Utilizzato per separare l'accesso al database dalla logica
applicativa.

SERVICE LAYER
-------------

Utilizzato per concentrare la logica applicativa e coordinare
più operazioni del Repository.

MODULE PATTERN
--------------

Utilizzato nel frontend JavaScript tramite ES Modules.

Questo permette di separare le responsabilità e ridurre
le dipendenze globali.

32. MANUTENIBILITA'
======================================================================

Il codice deve mantenere una separazione chiara delle responsabilità.

Evitare:

- query SQL direttamente nel frontend
- logica applicativa nelle API
- duplicazione delle query
- manipolazione diretta del database dal frontend
- dipendenze circolari tra moduli JS
- variabili globali non necessarie


Preferire:

- funzioni con responsabilità singola
- Repository riutilizzabili
- Service per operazioni complesse
- moduli JS indipendenti
- funzioni API centralizzate
- transazioni per operazioni atomiche

33. PRINCIPIO GENERALE DEL PROGETTO
======================================================================

Il principio architetturale principale è:

    PRESENTAZIONE
          |
          v
        API
          |
          v
      BUSINESS LOGIC
          |
          v
       REPOSITORY
          |
          v
       DATABASE


Ogni livello deve avere una responsabilità specifica.

Il frontend gestisce principalmente:

    interfaccia
    stato temporaneo
    interazione utente

Le API gestiscono:

    HTTP
    input/output
    validazione iniziale


I Service gestiscono:

    logica applicativa
    orchestrazione
    transazioni


I Repository gestiscono:

    persistenza
    query
    relazioni database


Il database gestisce:

    persistenza dei dati
    vincoli
    integrità referenziale


======================================================================
34. PRINCIPI DI SVILUPPO
======================================================================

1. Il client non è una fonte attendibile.

2. La validazione definitiva deve essere eseguita dal backend.

3. Le operazioni multi-step devono utilizzare transazioni.

4. I dati storici degli scontrini devono essere indipendenti
   dai successivi cambiamenti del menu.

5. Le responsabilità devono essere separate tra API,
   Service e Repository.

6. Le chiamate frontend devono essere centralizzate
   quando possibile.

7. Gli errori devono essere gestiti esplicitamente.

8. Le query devono utilizzare prepared statements.

9. Le credenziali non devono essere presenti nel codice sorgente.

10. Il codice deve privilegiare manutenibilità e prevedibilità
    rispetto a soluzioni rapide.
